## 0. 审计修订 2A-2（不要改）

1. **SFT 预览直接升级为 SFT-v1，不在 4090 上用 bf16 重训。**
   - 预览没有出现数值问题：0 步被跳过，loss scale 一直是 65536，val loss 在第 2 个 epoch 已经收平。
   - 用 bf16 重训，得到的基本是同一个模型，而后面的 GRPO 题集是用这个模型校准的。重训以后校准就得重做，换来的只有精度上的一点差别。
   - 正式的 SFT-v1 是 `runs/sft-preview/adapter-epoch2`（fp32 LoRA）。复制到 `runs/sft-v1/adapter/`，记下 sha256。
   - 上服务器以后，把这个适配器合并到 **bf16 的原始基座**上，得到 GRPO 的起点。不要用本地的 fp16 `merged/`：fp16 转 bf16 会丢 3 位尾数。
   - 服务器上要先在 dev 集上做一次一致性检查，见第 4 步的启动脚本。
2. **GRPO 不用现成框架，自己写一个最小实现。** 理由：
   - 本项目踩过的最大的坑是 token 一致性（修订 2A-1 第 2 条），而 SFT 这边已经有一套验证过的按轮渲染方式（`arl.sft.data`，4410 个前缀和 vLLM 逐 token 比对，0 处不一致）。自己写的话，rollout、训练、评测可以共用这一套。用框架，要先弄清它怎么处理 Qwen3 去掉 think 块这件事，而且换个版本就可能变。
   - 环境、判分和 episode 循环可以原样复用，不用改成框架要求的接口。
   - 算法本身很简单：每批采样只更新 1 次梯度（严格 on-policy，重要性比值恒为 1），不需要 critic，也不需要 PPO 裁剪。
   - 代价是正确性全靠自己的测试来保证。所以第 3 步要求单元测试，还要在本地做一个"能学会"的过拟合测试。
3. **rollout 改用 token 级接口。** 我们自己用已验证的渲染器生成 prompt 的 token id，调用 vLLM 的 `/v1/completions`（prompt 直接传 token id 列表），拿回生成的 token id 和 logprob，再用自己的 hermes 解析器解析工具调用。这样采样用的 token 和训练用的 token 从构造上就是同一份。从这一步起，校准、GRPO 和最后的留出集评测都只用这一个客户端。
4. **采样温度**：GRPO 的 rollout 和校准都用 temperature 1.0，这样采样分布就是模型本身的分布，训练算 logprob 时不需要额外做温度缩放。评测沿用 0.8，和之前所有 dev 结果的口径一致。
5. **GRPO 题集**：用 SFT-v1 在 `rl_train_ids` 上校准，每题 4 次，保留解出 1–3 次的题。dev 和留出集不进 GRPO 训练。

### 审计修订 2C-1

1. **把贪心比对的硬性判定换成回放比对。**
   - 新的判定：给定同一段完整历史，新客户端和 chat 接口做贪心生成，逐轮比较，至少 95% 的轮次完全一致；而且每一处不一致都要能归到数值上的非确定性，也就是对同一请求重新发一次能复现记录、或者复现不出来。只要有一处是渲染或解析造成的，这一项就不通过。
   - 这次是 64/65 = 98.5%，唯一不一致的那一轮属于数值上的非确定性，所以第 1 步通过。
   - 整条轨迹的贪心比对改为参考指标。CHECKPOINT 里要同时报告新客户端对旧客户端、旧客户端对自己这两组数。
   - 理由：环境里 `run_tests` 的输出带有函数内存地址和耗时，一旦跑过一次失败的测试，下一轮的 prompt 就不一样了。这就是 rollout 本来的随机性，不影响训练是否正确。训练要保证的是对同一段输入，采样用的 token 和训练用的 token 是同一份，回放比对验证的正是这一点。
2. **环境保持 `phase1-env-v1` 不变。** 不对工具输出里的内存地址和耗时做规范化，否则冻结的环境就变了，之前所有的结果也就没法比了。这条写进 `HELDOUT-PREREG` 的已知局限：贪心评测无法逐 token 复现，所有结论都按 K=4 采样的统计量来下。
3. **采样参数，确认你的做法：**
   - 评测配置不设 `top_k`，这样服务端用默认值 20，和之前的 dev 结果可比。`HELDOUT-PREREG` 里要写明：评测时 temperature 0.8、top_p 1.0、top_k 20（服务端默认）。为了以后不受默认值影响，评测配置里也要显式写上 `top_k: 20`，并说明这和之前不设的效果一样。
   - 校准和 GRPO 用 temperature 1.0、top_p 1.0、`top_k: 0`。这时采样分布和 vLLM 返回的 raw logprob 是同一个分布，TIS 比值才有意义。第 3 步要写一个测试：配置里这三个值不是 (1.0, 1.0, 0) 就拒绝启动 GRPO。
4. **第 2 步先做一次试点。** 从 `rl_train_ids` 按函数分层抽 50 题，每题 K=4，用校准配置（T=1.0，top_k=0）。之前没在完整分布下采过样，1.7B 模型可能会多出不少格式错误。
   - 报告：严格解出率、出现格式错误的 episode 比例、解出 1–3 次的题所占比例、平均轮数，以及和 dev 上 T=0.8、top_k=20 那组结果的对比。
   - 停止条件：出现格式错误的 episode 超过 15%，或者严格解出率低于 30%，就停下报告，不要自己改温度或 top_k。
   - 没触发停止条件，就接着跑全量校准。试点的 50 题照常并入全量，不用重跑。
5. **第 3 步本地显存调度的备选方案。** 如果 sleep mode 在 WSL 上起不来（比如 cumem 分配器不支持），本地的过拟合测试就退回"每步重启 vLLM"：采样完关掉 vLLM，训练，再带着新的适配器重启 vLLM。
   - 这只用于本地验证算法能不能学，不是正式方案。sleep mode 失败的报错和每步的耗时都要记下来。
   - 能不能用 sleep mode、能不能和训练端同时驻留显存，放到服务器上的 `bench.sh` 里确认。
   - 这时"同步后贪心生成和训练端一致"的检查照做，比较的对象换成重启后加载的适配器。
6. **第 3 步补一条检查。** 每次权重同步后，用 rollout 保存的一条已有轨迹，训练端用新的适配器算一遍 logp，vLLM 用新适配器对同一段 token 算一遍 prompt logprob，两边对比，报告平均绝对差。超过 0.05 就停下。理由：贪心生成只验证 argmax，这条检查能验证整个分布。

### 审计修订 2C-2

1. **采样参数保持 T=1.0、top_p 1.0、top_k 0，不变。试点按新判定通过，接着跑全量校准。** 理由：
   - **门槛的度量选错了。** "至少出现一次格式错误的 episode 比例"会随轮数增长：每次调用的错误率是 p，n 次调用后就是 1-(1-p)^n。试点的平均轮数和用满 10 轮的比例都比 dev 高，所以这个指标被抬高了，它反映的不只是采样分布。真正反映分布的指标是每次调用的错误率，试点是 3.45%，dev 是 1.72%，在完整分布下只多了约 1.7 个百分点，很低。
   - **格式错误不会结束 episode。** 工具会返回错误信息，模型可以接着改。36 个出错的 episode 里，29 个只错了 1 次。至于"出错的 episode 很少解出"，主要是因为用满 10 轮的失败 episode 调用次数多、出错机会也多，不能说明格式错误导致了失败。
   - **GRPO 本身会压低格式错误。** 出错的 episode 大多拿 0 分，在组内是负优势，错误的那些 token 会被直接惩罚。这是 RL 要学的东西之一，不应该在采样阶段就挡掉。
   - **保持完整分布换来的是正确性。** 采样分布和 vLLM 返回的 raw logprob、训练端算出的 logp 是同一个分布，TIS 比值就是严格的重要性比值。换成 top_k 20 或降低温度，要么训练端得跟着做同样的截断和缩放，要么 TIS 修正的就不再是同一个分布。为了少一点格式错误付出这个代价，不值得。
   - **难度区间的比例是够的。** 试点里解出 1–3 次的题占 38%，按 1853 题算约 700 题，高于门槛 400。
2. **格式门槛改用每次调用的错误率。** 校准和后面所有采样都用这个口径：每次工具调用的格式错误率不超过 6%，大约是 dev 口径的 3.5 倍。"至少出错一次的 episode 比例"照常报告，不作为门槛。全量校准跑完，如果每次调用的错误率超过 6%，就停下报告。
3. **GRPO 增加两项监控和一项停止条件：**
   - 每一步记录每次调用的格式错误率和出错 episode 的比例，并在 CHECKPOINT 里报告它们在训练中的变化趋势，预期是下降。
   - 每一步记录 completion token 的平均熵。熵由训练端的 logits 计算，只在 completion 位置上算，每个 token 一个值，再取平均；不参与求导。用来发现策略坍缩。
   - 停止条件：连续 10 步的每次调用格式错误率均值超过 10%，或者平均熵低于前 5 步均值的 30%，就停下报告。
   - 本地过拟合测试只跑 30 步，熵的条件也照样检查，并报告熵的曲线。
4. **以后定新门槛，先选对度量。** 凡是会随轮数或长度增长的指标，都不能直接当门槛，要先换算成每次调用或每个 token 的口径。这一条写进计划第 1 节"规则"。

### 审计修订 2C-3

1. **学习率改成 1e-5，过拟合测试单独用 5e-5。**
   - 原计划的 1e-6 是全参数 GRPO 的常用值。LoRA 需要的学习率一般是全参数的 10 倍左右，SFT-v1 用的就是 1e-4。AdamW 对 loss 的整体缩放基本不敏感，`T_norm` 取常数不会改变每步的更新幅度，所以 1e-6 在 30 步里很可能什么都学不到，过拟合测试会因为学习率而失败，而不是因为代码有错。
   - 正式配置 `configs/grpo/v1.json`：`lr` 改成 1e-5，常数，不加 warmup。
   - 过拟合配置 `configs/grpo/overfit-local.json`：`lr` 用 5e-5。这个测试只验证"梯度方向对、整条链路能学"，不验证正式超参数；学习率大一点，30 步里信号才清楚。两个值和理由都写进配置旁边的说明和 PROGRESS。
2. **训练、采样、评测全部统一用 fp16，取消 bf16 合并。** 这条替换修订 2A-2 第 1 条里"合并到 bf16 原始基座"的部分。理由：
   - SFT-v1 是在 fp16 基座上训练的，本地校准、dev 评测、`configs/grpo/v1.json` 的训练和 vLLM（`dtype: half`）也都是 fp16。服务器上只把 SFT-v1 改成 bf16，反而是唯一一处和别处不一致的地方：GRPO 题集是用 fp16 模型校准的，起点却换成 bf16，校准就不再对应起点了。
   - 原始基座是 bf16 存的。bf16 转 fp16 时，只有绝对值极小（低于约 6e-5）的权重会损失精度，正常范围内的值在 fp16 里都能精确表示。反过来，把 fp16 合并结果转成 bf16 会丢 3 位尾数。所以全程 fp16 比全程 bf16 更贴近 SFT-v1 训练时的模型。
   - RL 里训练端和推理端的 logprob 差异，fp16 一般比 bf16 小，这对 TIS 和 `max_logprob_diff_mean` 停止条件有利。fp16 的数值稳定性在本项目里已经验证过：SFT 训练 0 步跳过，所有 dev 评测和校准都用 fp16 跑，没有出过问题。
   - 具体改动：
     - `scripts/server/merge_bf16.sh` 改名为 `merge_fp16.sh`：把适配器合并到 fp16 基座，vLLM 用 `--dtype half` 服务，在 dev 集上用 token 客户端评测，严格解出率要落在 [45.5%, 61.25%]。
     - 本地也跑一遍 `merge_fp16.sh`，得到本地基线数字，写进 PROGRESS。服务器上再跑一次对照。
     - 写一个小检查：把基座的 bf16 权重转成 fp16 再转回来，报告有多少个元素发生变化、最大绝对误差多少，结果写进 PROGRESS。
3. **修改留出集预注册。** GRPO 还没有开始，现在修改符合"开始 GRPO 之前提交"的规定，但要公开留痕：
   - 在 `HELDOUT-PREREG.zh-CN.md` 末尾加一节"修订记录"，写明日期、改了什么、为什么改。原文不删，git 历史里能查到。
   - 改动内容：三个模型在留出集上一律以 fp16 合并模型的形式、用 vLLM `--dtype half` 评测（基座直接用 fp16 加载）。SFT-v1 是 `merge_fp16.sh` 的结果。GRPO 选定的检查点也先合并成 fp16 再评测，不用 vLLM 的运行时 LoRA，避免 LoRA kernel 和合并权重之间的数值差别。
   - GRPO 训练中的 dev 评测仍然用运行时 LoRA，因为它只用来选检查点。这一点写进已知局限。
   - "已知局限"里关于 bf16 的那条改成 fp16 的说法。

4. **先查清 OOM 的原因，用数值等价的办法降显存，再重跑本地过拟合测试。** SFT 在同样 8192 的上下文下峰值只有 9.16 GiB，GRPO 训练端却多要 1.2 GiB 以上。可疑点在 `loss.py` 的 `train_step`：
   - `completion_logits` 把所有 completion 位置的整词表 logits（约 15 万维）转成 fp32；
   - `cross_entropy` 的梯度又是一份同样大小的张量；
   - `token_entropy` 在计算图还没释放时，又基于整块 logits 生成好几份 n×V 的中间结果。

   要做的：
   - **先测量**：取过拟合训练集里 completion 最长的那条序列，单独做一次前向和反向，用 `torch.cuda.memory_allocated` 分段记录：模型权重、前向之后、logits、熵、反向峰值。结果写进 PROGRESS。
   - **再修改**：只允许数值上等价的改动。
     - 熵按 completion 位置分块计算，比如每块 256 行，并且放在 `backward()` 之后，用已经 detach 的 logits 来算，或者干脆在 no_grad 下单独再前向一次，取显存更省的那种。
     - logp 用分块的 `log_softmax` 加 gather 计算，或者分块计算 lm_head 和 cross entropy。
     - 不允许改的：上下文长度、`max_turns`、LoRA 配置、`cuda_memory_limit_gib`；也不允许丢掉长序列、截断序列。
   - **证明等价**：写测试，在 CPU 上用小模型比较新旧实现的 loss、各参数的梯度和熵，误差都要在 1e-5 以内。
   - **重跑本地过拟合测试**：用修订后的过拟合配置（lr 5e-5），memory_mode 先用 sleep；sleep 放不下再用 restart。验收标准不变：8 题、30 步，平均奖励比训练前的 0.375 至少高 0.15；其他停止条件照旧。报告奖励曲线、熵曲线、每次调用的格式错误率曲线、每一步的分段耗时和显存峰值。
   - **如果数值等价的办法用完还是 OOM**：停下报告，把测量数据贴出来。不要改其他设置。这时本地过拟合测试改到服务器上，作为 `bench.sh` 之前的第一项来做。
5. **为服务器驱动版本准备一套备用环境。** `setup.sh` 要求驱动支持 CUDA 13.0（驱动 580 以上），但租用平台上很多机器的驱动还是 535 或 550（CUDA 12.x）。
   - 查 vLLM 0.31.0 和 torch 2.13.0 有没有官方的 cu128 或 cu126 wheel，以 PyPI 和官方下载页为准，查到的写进 PROGRESS。
   - 如果有：生成 `requirements-train-cu128.txt`，以及对应的 vLLM 安装方式。在本机建一个独立环境 `~/.venvs/vllm-cu128`（本机驱动较新，可以向下兼容运行 cu128），在里面跑全量测试，再跑一次逐轮 tokenize 比对和回放比对（修订 2C-1 第 1 条的新判定），确认和主环境的结果相同。
   - `setup.sh` 改成：先读驱动的 CUDA 版本，13.0 以上用主环境；12.8 以上、13.0 以下用备用环境；更低就停下。
   - 如果官方没有可用的 wheel：停止准备备用环境，在 `sync.md` 里写明"租机时必须选驱动 580 以上的镜像"。

## 1. 规则

- 之前的规则全部有效：在 WSL 里工作；每一步做完跑全量测试、提交、写 PROGRESS；每次提交前做密钥检查；遇到"停下报告"不得自行降低要求。
- 本阶段不调用付费 API。
- 训练代码放 `src/arl/rl/`，测试放 `tests/rl/`，依赖 torch 的部分沿用 `~/.venvs/train` 的约定。新依赖要先在 PROGRESS 里写明理由。
- 本地 GPU 一次只跑一个进程，vLLM 和训练不能同时占显存。所有 PyTorch 进程都设 `expandable_segments` 和显存上限（CHECKPOINT-2A"遇到的问题"第 1 条）。
- 留出集只在第 5 步写预注册时读取题号和统计信息，不跑任何模型。
- 以后定新门槛，先选对度量。凡是会随轮数或长度增长的指标，都不能直接当门槛，要先换算成每次调用或每个 token 的口径（审计修订 2C-2 第 4 条）。

## 2. 分步计划

### 第 1 步：冻结 SFT-v1，实现 token 级 rollout 客户端

- **冻结 SFT-v1。** 把 `adapter-epoch2` 复制到 `runs/sft-v1/adapter/`。在新文件 `configs/sft/v1.json` 里记录这些信息：
  - 基座快照 `70d244cc86cc`；
  - 适配器各文件的 sha256；
  - 训练数据 `data/sft/v2` 的 sha256；
  - 训练配置文件的路径。
  
  适配器本身不入库，只提交这份 json。然后打 tag `sft-v1`。
- **实现 `src/arl/rollout/tokenclient.py`。**
  - 每轮的流程：
    1. 用 `arl.sft.data` 的渲染器，对当前消息加 `add_generation_prompt=True` 渲染出 prompt token id；
    2. 调用 `/v1/completions`，`prompt` 直接传 token id 列表，并带上 `return_token_ids`、`logprobs=0`。参数名以 vLLM 0.31 的文档为准，查到的写进 PROGRESS；
    3. 生成以 `<|im_end|>` 结束。用我们自己的 hermes 解析器解析工具调用，解析规则和现在 parser 的严格程度一致。
  - 每轮都要保存：`prompt_ids`、`completion_ids`、`completion_logprobs`、`finish_reason`。保存的就是采样时实际用的 token，训练时原样使用，不再重新渲染。
  - 接口要和现有客户端一致，这样 `run_episode` 不用改就能接上。
- **一致性检查（必须有）：**
  - **逐轮比对：** 对每一轮，`prompt_ids` 等于 vLLM 服务端 `/tokenize` 的结果，用原始消息加 tools 和 `enable_thinking=False`。
  - **贪心比对：** 从 dev 集抽 10 题，temperature 0，旧客户端（chat 接口）和新客户端各跑一遍，逐 episode 比较工具调用序列和奖励。至少 9 题完全一致。不一致的要贴出差异，并分析是 batch 的非确定性，还是渲染或解析不同。
  - **统计比对：** 用新客户端在 dev 集上评测 SFT 模型，K=4、temperature 0.8。严格解出率要落在 53.5% 的 bootstrap 95% 置信区间里。不在区间里就停下报告。
- 测试、提交。从这里开始，校准、GRPO 和评测都只用新客户端。

### 第 3 步：GRPO 最小实现 `src/arl/rl/`

**算法**（写进 `configs/grpo/v1.json`，本地测试和服务器正式训练共用这套代码）：

- 每一步从 `grpo_v1_ids` 取 `n_tasks` 道题，每道题采 `G` 条 rollout。默认 `n_tasks` 16、`G` 8，temperature 1.0。
- **优势**：每组内 `A_i = r_i - mean(r)`，不除以标准差，也就是 Dr. GRPO 的做法：除以标准差会放大接近全对、全错那些组的噪声。全对或全错的组 A 全为 0，直接跳过，跳过的比例要计数。
- **loss**：只在每轮的 `completion_ids` 上计算，工具结果、system 和 user 部分不参与。`loss = -Σ_i A_i · Σ_{t∈i} logp_t / T_norm`，其中 `T_norm` 取固定常数 `n_tasks · G · max_completion_tokens_per_episode`，不按实际长度归一，避免长轨迹被稀释。
- **严格 on-policy**：每批 rollout 只做 1 次优化器更新，不用 PPO 裁剪，不用 critic。KL 系数 β 设为 0，但每一步都要记录对 SFT-v1 参考模型的 KL 估计（k3 估计量，用 rollout 的 token 算）。
- **训练和推理的 logprob 差异**：每一步统计训练端算出的 logp 和 vLLM 返回的 logprob 差多少，记录均值、p99 和最大值。另外实现截断重要性采样（TIS，`ratio = exp(logp_train - logp_vllm)`，截断到不超过 2），由配置开关控制，默认打开。
- **模型和权重同步**：
  - 训练端是 SFT-v1 的 LoRA，继续训练同一个适配器，r 16，学习率 1e-6 起，具体值写进配置；
  - vLLM 用 `--enable-lora` 启动，每一步结束后保存适配器，用运行时 LoRA 加载接口热加载，请求里指定新的适配器名。接口名以 vLLM 0.31 文档为准。
  - 每次加载以后，先用一条固定 prompt 做贪心生成，确认输出和训练端一致，再继续下一步。
- **显存调度**：
  - 本地 11 GB 放不下 vLLM 和训练同时运行，用 vLLM 的 sleep mode 轮流用显存：采样完让 vLLM sleep，训练完再 wake up。
  - 4090 上先尝试两者同时驻留，放不下再退回 sleep mode。两种模式都写进配置，可以切换。
- **日志**（`runs/grpo-*/log.jsonl`）：每一步都要记：
  - 平均奖励，以及非全对全错组所占比例；
  - 损失、梯度范数、学习率；
  - KL 估计，logprob 差异的均值、p99、最大值，TIS 截断的比例；
  - 平均轮数、输出 token 数、停止原因分布；
  - 采样、训练、同步各用多少秒。
- **检查点**：每 `eval_every` 步保存一次适配器，并在 dev 集上评测：K=4，temperature 0.8，用第 1 步的新客户端，两种口径都记。

**测试**（在 `tests/rl/` 里，不需要 GPU 的部分放进主测试）：

- 优势计算：全对、全错、混合三种组。
- loss 只落在 `completion_ids` 上：构造一条多轮轨迹，检查 mask 的位置。
- 训练端的 token 序列：用 rollout 保存的 `prompt_ids` 和 `completion_ids` 拼起来，**不重新渲染**。这一点也要写测试。
- 一个很小的玩具测试：用一个随机初始化的小 transformer，奖励规则是"生成某个固定 token 得 1 分"。跑 50 步，平均奖励要从约 0 升到 0.8 以上。

**本地过拟合测试**（这一步的验收标准）：

- 从 `grpo_v1_ids` 里固定 seed 取 8 道题，只在这 8 道题上训练 30 步，`n_tasks` 8、`G` 8，用 sleep mode。
- 训练前后，在这 8 道题上各跑 K=8、temperature 1.0。训练后的平均奖励要比训练前高 0.15 以上。
- 报告每一步的耗时，按阶段分开（采样、sleep 和 wake、训练、同步），以及显存峰值。
- **停止条件**，满足任何一条就停下报告，不要自行改学习率或算法：
  - 奖励没有上升；
  - 出现 NaN；
  - logprob 差异的均值大于 0.05；
  - 权重同步以后贪心生成和训练端不一致。
