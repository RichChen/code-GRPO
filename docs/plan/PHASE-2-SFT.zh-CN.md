### 第 1 步：把训练集再分成 SFT 池和 RL 池

原因：如果 SFT 和 GRPO 用同一批题，SFT 模型在这些题上会接近全对，校准后会被大量筛掉，这样筛出来的难度也是有偏的。

- 只在 `train` 内部按**簇**划分（簇的定义和 `clustering` 一致）。固定 seed `sftsplit-0`，打乱簇的顺序，依次放进 SFT 池，直到 SFT 池的 bug 来源函数达到训练集的 40%，其余的簇都归 RL 池。
- 输出 `data/tasks/train_sft_ids.txt` 和 `train_rl_ids.txt`，每行一个题号。原来的 jsonl 不动，把这两个文件的 sha256 写进新文件 `data/tasks/phase2-split.json`。
- 写测试：同一个簇不能跨两个池；两个池的并集就是完整的训练集，交集为空；留出集的题不能出现在这两个文件里。
- 报告两个池各有多少题、多少来源函数、bug 类型怎么分布。

### 第 2 步：用 DeepSeek 采集轨迹（只在 SFT 池上采）

- 环境用 `phase1-env-v1`，模型 `deepseek-flash`，非思考模式，`temperature` 0.8，`max_tokens` 1024。
- 每题跑 1 次；失败的题再补跑 1 次，每题最多 2 次。
- 成功轨迹的上限是 1500 条，花费上限 15 元，先到哪个就停。
- 原始结果写进 `runs/deepseek-sft/episodes.jsonl`，要能断点续跑。

### 第 3 步：构建 SFT 数据集 `src/arl/sft/data.py`

**筛选**：每条轨迹必须同时满足下面全部条件才保留，否则丢弃，并按原因计数：

- 奖励是 1；
- 没有格式错误，没有被提醒，没有因为上下文超长被截断；
- 轮数不超过 8；
- 只修改了 `pkg/` 下的文件，没有动可见测试；
- 同一道题最多保留 1 条，同一个来源函数最多保留 3 条。

**渲染**：这一步最关键，训练时的 token 必须和推理时完全一致。

- 用 Qwen3-1.7B 自带的 chat template 渲染，参数 `enable_thinking=False`，tools 用环境实际给模型的那份 schema。
- 每条 assistant 消息都要写成模型推理时会生成的样子，也就是 hermes 格式的 `<tool_call>{json}</tool_call>`，前面加上模板在非思考模式下插入的空 think 块，具体以模板实际输出为准。
- DeepSeek 返回的 `tool_calls` 是结构化的，要转换成上面的文本格式。参数 JSON 统一用 `json.dumps(..., ensure_ascii=False)` 序列化。
- 只在 assistant 生成的 token 上计算 loss，包括结尾的 `<|im_end|>`。system、user 和工具结果全部 mask 掉。

**一致性测试**（必须有）：

- 对每条轨迹的每个 assistant 轮，分别做两件事：
  - 用模板对它之前的消息 `add_generation_prompt=True` 渲染一次，得到前缀；
  - 把这一轮的 assistant 文本接在前缀后面。

  两者的 token 序列必须逐个相同。
- 把这一轮的 assistant 文本交给 vLLM 的 hermes parser 解析，解析出来的工具调用必须和原轨迹一致。

不一致的样本一律丢弃并计数。不一致的超过 2%，就停下报告。

**输出**：

- `data/sft/v1/{train,val}.jsonl`。按来源函数切出 5% 作为验证集，这里的验证集只用来看 loss，和留出集无关。
- 外加 `stats.json`，记录：样本数、token 长度分布（中位数、p95、最大值）、assistant token 占比、每种丢弃原因的计数、bug 类型分布。
- `data/sft/` 加入 `.gitignore`，只提交 `stats.json`。

如果筛选后的样本少于 800 条，就停下报告。

**审计修订 2A-1**

1. **每个来源函数最多保留 5 条（原来是 3 条），门槛 800 条不变。** 预计能保留 880 条。
   - 不取消上限。135 个函数有 4 条以上，不设上限的话，少数函数的写法会在 SFT 里占比过大。
   - 不扩大 SFT 池。RL 池的函数数量直接决定 GRPO 校准后还能剩多少题，比 SFT 多几百条更重要。
   - 这一阶段 SFT 的目的是教会工具格式和"读、改、测"的流程，不是灌知识，所以 880 条够用。SFT 做得太强，反而会压低策略的多样性，GRPO 就更难采到有差异的样本。
   - 同一个函数内部怎么选，规则不变：优先选还没选过的 bug 类型，用 `sftdata-0` 打乱。
2. **确认按轮切样本的渲染方式。** 本地预览按现在的估算是 906 万 token，代价可以接受，不改推理端模板。另外记一条，留给 2B：多轮 GRPO 同样会遇到"历史轮去掉 think 块"的问题。到 2B 选框架时必须先定下来：采样时用的 token 序列和训练时算 logprob 用的序列，是不是同一份；评测时的渲染方式和这两者是否一致。不能各用一套。
3. **确认 fp16 下溢出的判定方式。** 前向 loss 出现 inf 或 NaN 就停止；梯度溢出交给 GradScaler 跳过这一步，并且计数。在原来的停止条件之外再加一条：被跳过的步数超过总步数的 5% 就停止。训练日志和 CHECKPOINT 里都要报告被跳过了多少步。
4. **dev 集不能进 GRPO 训练。** dev 集是从 RL 池里抽的。阶段 3 的 GRPO 训练集是 RL 池去掉 dev 集剩下的题，dev 集只用于选模型和做诊断。现在就在 `phase2-split.json` 里新增 `rl_train_ids` 这个口径（等于 RL 池减 dev 集），记下题数、函数数和 sha256，并写测试保证它和 dev 集不相交。
5. **干扰函数跨池的问题不处理，不重新组装题集。** 理由：
   - SFT 池和 RL 池分开，是为了让 GRPO 的难度校准不受 SFT 影响，不是为了防泄漏。防泄漏靠的是留出集，而留出集和训练侧在簇这一级完全分开。
   - 干扰函数是没有被改坏的正确代码。SFT 时见过它们，最多让模型更容易排除这些函数，偏差很小，而且方向是已知的。

   在 CHECKPOINT 里把这一点写成 dev 集结果的已知局限：dev 上的 SFT 增益可能略偏乐观，最终以留出集为准。
6. **加一组参考评测：DeepSeek 在 dev 集上跑一遍。** 每题 K=4，环境 `phase1-env-v1`，配置和第 2 步一样，花费另记在 `runs/deepseek-dev/cost.json`，上限 5 元。作用是给 dev 集一个能力上限，用来判断哪些题是 1.7B 解不出、而题本身是能解的。这一组不参与任何选择。
7. 本阶段付费 API 的总上限调整为 25 元，包括已经花掉的 9.85 元。

### 第 4 步：本地 SFT 预览 `src/arl/sft/train.py`

目的是在 2080 Ti 上验证整条链路：数据能训、loss 会降、训完的模型确实变好。这一步的结果**不是正式结果**。正式训练在 2B 用 bf16 做，超参数也会在那时重新确定。

- **环境**：在 `~/.venvs/train` 里装 torch（版本要和 WSL 里的 CUDA 驱动匹配）、transformers、peft。版本锁定在 `requirements-train.txt`。不用 TRL、DeepSpeed、bitsandbytes。
- **配置**（写进 `configs/sft/preview.json`）：
  - 基座 `Qwen/Qwen3-1.7B`，权重按 fp16 加载；
  - LoRA：r=16，alpha=32，dropout 0.05，作用在全部 attention 和 MLP 的线性层上；
  - 适配器参数保持 fp32；前向用 fp16 autocast，配合 GradScaler；
  - 打开 gradient checkpointing；
  - `max_seq_len` 8192，样本超长就丢弃，不截断；
  - micro batch 1，梯度累积 16；
  - 学习率 1e-4，cosine 调度，warmup 3%；
  - 训练 2 个 epoch，seed 0。
- **记录**：每 10 步记一次 train loss、学习率、grad norm，每 100 步记一次 val loss，写进 `runs/sft-preview/log.jsonl`。
- **每一步都要检查**：loss 和 grad norm 是否出现 NaN 或 inf、GradScaler 的 scale 有没有一路降到 1 以下、显存峰值多少。
- **停止条件**，满足任何一条就停下报告，不要改成 fp32、改学习率或改 LoRA 配置：
  - 出现 NaN 或 inf，或者 scale 持续下降；
  - 显存不够（OOM）；
  - 估算总训练时间超过 12 小时；
  - 第一个 epoch 结束时 val loss 没有下降。
- 训完把适配器合并进基座，按 fp16 保存到 `runs/sft-preview/merged/`。这一目录不入库。

## 4. 审计修订 2A-2（替换原阶段 2B）

开头说的 2B（在 4090 上做正式的 bf16 SFT，加上原阶段 0 的框架冒烟测试）不再执行，由下面这条修订替换。后续工作见 `PHASE-2C-LOCAL-PREP.zh-CN.md`（阶段 2C：租卡前的本地准备）。以下是修订原文。

1. **SFT 预览直接升级为 SFT-v1，不在 4090 上用 bf16 重训。**
   - 预览没有出现数值问题：0 步被跳过，loss scale 一直是 65536，val loss 在第 2 个 epoch 已经收平。
   - 用 bf16 重训，得到的基本是同一个模型，而后面的 GRPO 题集是用这个模型校准的。重训以后校准就得重做，换来的只有精度上的一点差别。
   - 正式的 SFT-v1 是 `runs/sft-preview/adapter-epoch2`（fp32 LoRA）。复制到 `runs/sft-v1/adapter/`，记下 sha256。
   - 上服务器以后，把这个适配器合并到 **bf16 的原始基座**上，得到 GRPO 的起点。不要用本地的 fp16 `merged/`：fp16 转 bf16 会丢 3 位尾数。
   - 服务器上要先在 dev 集上做一次一致性检查，见第 4 步的启动脚本。
2. **GRPO 不用现成框架，自己写一个最小实现。** 理由：
   - 本项目踩过的最大的坑是 token 一致性（修订 2A-1 第 2 条），而 SFT 这边已经有一套验证过的按轮渲染方式（`arl.sft.data`，4410 个前缀和 vLLM 逐 token 比对，0 处不一致）。自己写的话，rollout、训练、评测可以共用这一套。用框架，要先弄清它怎么处理 Qwen3 去掉 think 块这件事，而且换个版本就可能变。
   - 环境、判分和 episode 循环可以原样复用，不用改成框架要求的接口。
   - 算法本身很简单：每批采样只更新 1 次梯度（严格 on-policy，重要性比值恒为 1），不需要 critic，也不需要 PPO 裁剪。
   - 代价是正确性全靠自己的测试来保证。所以第 3 步要求单元测试，还要在本地做一个"能学会"的过拟合测试。
3. **rollout 改用 token 级接口。** 我们自己用已验证的渲染器生成 prompt 的 token id，调用 vLLM 的 `/v1/completions`（prompt 直接传 token id 列表），拿回生成的 token id 和 logprob，再用自己的 hermes 解析器解析工具调用。这样采样用的 token 和训练用的 token 从构造上就是同一份。从这一步起，校准、GRPO 和最后的留出集评测都只用这一个客户端。
4. **采样温度**：GRPO 的 rollout 和校准都用 temperature 1.0，这样采样分布就是模型本身的分布，训练算 logprob 时不需要额外做温度缩放。评测沿用 0.8，和之前所有 dev 结果的口径一致。
5. **GRPO 题集**：用 SFT-v1 在 `rl_train_ids` 上校准，每题 4 次，保留解出 1–3 次的题。dev 和留出集不进 GRPO 训练。
