## 审计修订 2A-1

1. **每个来源函数最多保留 5 条（原来是 3 条），门槛 800 条不变。** 预计能保留 880 条。
   - 不取消上限。135 个函数有 4 条以上，不设上限的话，少数函数的写法会在 SFT 里占比过大。
   - 不扩大 SFT 池。RL 池的函数数量直接决定 GRPO 校准后还能剩多少题，比 SFT 多几百条更重要。
   - 这一阶段 SFT 的目的是教会工具格式和"读、改、测"的流程，不是灌知识，所以 880 条够用。SFT 做得太强，反而会压低策略的多样性，GRPO 就更难采到有差异的样本。
   - 同一个函数内部怎么选，规则不变：优先选还没选过的 bug 类型，用 `sftdata-0` 打乱。
2. **确认按轮切样本的渲染方式。** 本地预览按现在的估算是 906 万 token，代价可以接受，不改推理端模板。另外记一条，留给 2B：多轮 GRPO 同样会遇到"历史轮去掉 think 块"的问题。到 2B 选框架时必须先定下来：采样时用的 token 序列和训练时算 logprob 用的序列，是不是同一份；评测时的渲染方式和这两者是否一致。不能各用一套。
3. **确认 fp16 下溢出的判定方式。** 前向 loss 出现 inf 或 NaN 就停止；梯度溢出交给 GradScaler 跳过这一步，并且计数。在原来的停止条件之外再加一条：被跳过的步数超过总步数的 5% 就停止。训练日志和 CHECKPOINT 里都要报告被跳过了多少步。
4. **dev 集不能进 GRPO 训练。** dev 集是从 RL 池里抽的。阶段 3 的 GRPO 训练集是 RL 池去掉 dev 集剩下的题，dev 集只用于选模型和做诊断。现在就在 `phase2-split.json` 里新增 `rl_train_ids` 这个口径（等于 RL 池减 dev 集），记下题数、函数数和 sha256，并写测试保证它和 dev 集不相交。
5. **干扰函数跨池的问题不处理，不重新组装题集。** 理由：
   - SFT 池和 RL 池分开，是为了让 GRPO 的难度校准不受 SFT 影响，不是为了防泄漏。防泄漏靠的是留出集，而留出集和训练侧在簇这一级完全分开。
   - 干扰函数是没有被改坏的正确代码。SFT 时见过它们，最多让模型更容易排除这些函数，偏差很小，而且方向是已知的。

   在 CHECKPOINT 里把这一点写成 dev 集结果的已知局限：dev 上的 SFT 增益可能略偏乐观，最终以留出集为准。
6. **加一组参考评测：DeepSeek 在 dev 集上跑一遍。** 每题 K=4，环境 `phase1-env-v1`，配置和第 2 步一样，花费另记在 `runs/deepseek-dev/cost.json`，上限 5 元。作用是给 dev 集一个能力上限，用来判断哪些题是 1.7B 解不出、而题本身是能解的。这一组不参与任何选择。
7. 本阶段付费 API 的总上限调整为 25 元，包括已经花掉的 9.85 元。
