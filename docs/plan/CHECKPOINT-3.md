### 第 4 条：提速

- **关闭梯度检查点：没做。** colocate、vLLM 0.45、最坏序列（8192 token、completion 1024）的条件下，训练端上限设为 19 GiB 时 OOM。已分配 18.79 GiB 时还要再分配 96 MiB，所以峰值至少约 18.9 GiB，超过 18 GiB 门槛，按修订跳过。
  - **因此没有做开关检查点的等价性检查，没有实测的 loss 或梯度差值，也没有省时数据。**
- **KL 随机抽样：做了。** `kl.max_sequences` 64，按 `(seed, step)` 固定种子随机抽。
  - 顺带修了 KL 配对的问题：原来用 `zip(kept, seqs)`，只在取前 n 条时才对得上。
  - 正式训练每步 `kl_sequences` = 64。
- **提速前后的步时**：
  - 提速前，正式规模没有实测。第 3 步按过拟合外推的结果是单步约 390 秒（KL 用全部序列）。
  - 提速后，3 步测速是 372 秒；整个正式训练平均 353 秒（采样 74 秒，训练 275 秒，保存 3 秒，同步 0.5 秒）。
  - 两次批次不同，拆不出 KL 抽样单独省了多少。训练端主要的时间花在逐条序列的前向和反向，加上梯度检查点的重算。

## 预注册里的已知局限，逐条说明实际影响

1. **干扰函数跨池，dev 上的 SFT 增益可能偏乐观。** 留出集的来源函数和训练侧分开。SFT − 基座在本地 dev 上是 +33.3（K=4，CHECKPOINT-2A），在留出集上是 +33.2，几乎一样。这次没有看到明显的偏乐观。
2. **生成用例约 1.5% 假阴性。** 对三个模型都一样，基本是同一批题上的系统性偏差，对配对差值影响很小。绝对解出率可能都低估了约 1 个百分点。
3. **SFT-v1 是本地 fp16 预览训练的适配器。** GRPO 从它出发，留出集上 SFT-v1 也是用它评测的，两者一致。这条只限制“SFT 能做到多好”的结论，不影响 GRPO − SFT 的比较。
4. **贪心评测无法逐 token 复现。** 所有结论都用 K=4 采样的统计量，没有用贪心轨迹做比较，没有影响。
5. **三个模型都以 fp16 评测。** 都满足：基座直接以 fp16 加载，SFT-v1 和 GRPO 都是合并后的 fp16 权重，vLLM `--dtype half`。服务器上 SFT-v1 合并结果在 dev 上是 55.5%，在区间内。
6. **训练中的 dev 评测用运行时 LoRA，留出集用合并权重。** 实测合并模型和“基座 + 适配器”的逐 token logprob 平均差 0.0055，只有适配器作用量（0.50）的约 1%。dev 只用来选检查点，三个候选（150、175、200）只差 6 个 episode，这点数值差别不会改变“选哪个”以外的结论。
