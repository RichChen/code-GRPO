## 2. 分步计划

### 第 1 步：装环境、自检、核对 SFT-v1

1. `scripts/server/setup.sh`。装 torch 2.13.0+cu130、vLLM 0.31.0，下载基座快照 `70d244cc86cc`。
   - 下载慢的话可以设 `HF_ENDPOINT=https://hf-mirror.com`（已测通），用了就写进 PROGRESS。
2. `scripts/server/selfcheck.sh`。必须全部通过，**13 项 bwrap 检查一项都不能跳过**。
3. **核对 SFT-v1**：算 `runs/sft-v1/adapter/` 里各文件的 sha256，和 `configs/sft/v1.json` 比对。
   - 不一致就停下报告，贴出两边的值和文件大小，不要自行更新 json 里的记录。
   - 适配器的权重张量要逐一检查有没有 NaN 或 inf，有就停下。
4. 提交，报告：各步耗时、磁盘占用、测试结果。

### 第 2 步：合并 fp16 并核对 dev 基线

1. `scripts/server/merge_fp16.sh`。把 SFT-v1 合并进以 fp16 加载的基座，vLLM 用 `--dtype half` 服务，在 dev 集上用 token 客户端评测，K=4、temperature 0.8、top_k 20。
2. **通过标准**：严格解出率落在 [45.5%, 61.25%] 内（本地 53.5% 的 95% 区间）。不在区间内就停下报告，不要重跑碰运气，也不要改评测参数。
3. 报告：严格口径和非 generated 口径的解出率、每次调用的格式错误率、平均轮数、停止原因分布，并和本地 53.5%、55.25% 这两个数对比。
4. 提交。

### 第 3 步：GRPO 过拟合测试（本地没跑成，这里是第一次真跑）

这一项是正式训练的前置条件。本地因为显存不够没能跑起来，这里要先跑通。

1. **先探测显存模式**：跑 `scripts/server/bench.sh` 的 probe 部分，确认 sleep level 1 和 2 能不能用、训练端和 vLLM 能不能同时驻留（colocate）。
   - 40 GB 下 colocate 应该放得下：vLLM 约 10 GB、训练端约 11 GB。能 colocate 就用它，每步能省掉 sleep 和 wake 的时间。
   - `configs/grpo/v1.json` 里的 `cuda_memory_limit_gib` 现在是 10.0，这是为 11 GB 的本地卡设的。按 colocate 的实测占用把它调到一个合适的值，比如 16.0，并说明依据。这是放宽本地的限制，不是改算法超参数。
   - `vllm.gpu_memory_utilization` 现在是 0.85。colocate 模式下要调低，让训练端有空间，建议从 0.45 起试。实际用的值和依据写进 PROGRESS。
2. **跑过拟合测试**：`configs/grpo/overfit-local.json`，8 题、30 步、lr 5e-5，`memory_mode` 用第 1 小步定下来的模式。
3. **通过标准**（和原计划一致）：训练后在这 8 题上 K=8、T=1.0 的平均奖励，比训练前至少高 0.15。
4. **停止条件**，触发任何一条就停下报告，不要改学习率或算法：
   - 奖励没有上升；
   - 出现 NaN；
   - logprob 差异均值大于 0.05；
   - 权重同步后贪心生成或 logprob 和训练端不一致；
   - 熵掉到前 5 步均值的 30% 以下。
5. 报告：奖励曲线、熵曲线、每次调用的格式错误率曲线、每一步按阶段分的耗时（采样、sleep 或 wake、训练、同步）、显存峰值、`max_logprob_diff` 的均值和 p99。
6. 提交。

### 第 4 步：正式 GRPO 训练

1. **先跑 3 步测速**：用 `bench.sh` 的后半部分，按实测步时估算 200 步要多久，写进 PROGRESS。
   - 估算超过 20 小时，就先停下报告，等审计方决定是减少步数还是调小 `n_tasks`。不要自行改配置。
2. **正式训练**：`configs/grpo/v1.json`，1018 题、200 步、`n_tasks` 16、`group_size` 8、lr 1e-5、T=1.0、top_k 0。每 25 步在 dev 集上评测一次并保存检查点。
   - 放在 tmux 里跑，要能断点续跑。
   - **每过约 2 小时在 PROGRESS 里追加一次简报**：步数、平均奖励、非全对全错组的比例、熵、格式错误率、logprob 差异、dev 评测结果。这样审计方中途也能判断要不要继续。
3. **停止条件**（配置里已有，触发就停）：连续 10 步格式错误率超过 10%；熵坍缩；logprob 差异均值超过 0.05；跳过的步数超过 3。
   - 另外加一条：如果到第 100 步，dev 严格解出率仍然没有超过第 0 步的基线，就停下报告。
4. **选检查点**：按 `HELDOUT-PREREG` 的规定，只看 dev 严格解出率，取最高；相差不到 1 个百分点时取步数更早的那个。选的理由和各检查点的 dev 结果都要写出来。
5. 提交。

## 审计修订 3-1

1. **过拟合测试的判定（A）**：用 `runs/grpo-overfit/adapters/step-13` 在同样的 8 道题上测一次 K=8、T=1.0。调用的 `measure` 和训练前那次是同一个函数，tag 用 `after-step13`，结果写进 `runs/grpo-overfit/log.jsonl`。
   - **通过标准**：平均奖励 ≥ 0.328 + 0.15 = 0.478。没达到就停下报告，不要做后面的 B。
2. **过拟合续跑（B，诊断用）**：
   - 先把 `runs/grpo-overfit` 整个复制到 `runs/grpo-overfit-cont`，原目录不动。新建配置 `configs/grpo/overfit-cont.json`：继承 `overfit-local.json`，`out_dir` 改为新目录，只把 `stop.entropy_collapse_ratio` 设为 0，等于关掉熵停止条件。其他停止条件全部保留。
   - 用 `--resume` 从第 13 步续跑到第 30 步，跑完做训练后测量，K=8，tag `after-step30`。
   - 如果 resume 因为配置和保存的状态不一致而拒绝启动，不要绕过校验。改法是在代码里加一个"resume 时允许改动的字段"白名单，只放 `stop.*` 和 `out_dir`，并补上测试。
   - B 不设通过标准，但下面两种情况要停下报告，**不要进入正式训练**：
     - 第 26–30 步 rollout 奖励的均值，比第 9–13 步的均值（0.622）低 0.1 以上；
     - `after-step30` 低于 `after-step13` 0.1 以上。

     这两种情况都说明熵掉得很低之后奖励会变差，正式训练的停止规则需要审计方重新看。
   - 报告逐步的奖励、熵、"有好有坏的组"的比例、每次调用的格式错误率、KL。
3. **正式训练的熵停止条件改成两个条件同时满足才停**：
   - 熵低于前 5 步均值的 30%；
   - 并且最近 10 步"有好有坏的组"的比例的均值低于 0.25。

   这种组的比例低于 0.25，意味着四分之三以上的组全对或全错，没有梯度，这时继续训练没有意义。只是熵下降、但组内仍有差异，不算坍缩。
   - 实现：在 `grpo.py` 的停止判定里加上第二个条件，新配置项 `stop.mixed_group_fraction_min: 0.25`、`stop.mixed_group_window: 10`。
   - 测试至少覆盖三种情况：熵低但组内有差异，不停；组内无差异但熵正常，不停；两者都满足，停。
   - 过拟合配置（`overfit-local.json`、`overfit-cont.json`）不受影响。
4. **提速：只做数值上等价、或者只影响日志的改动。**
   - **关闭梯度检查点**：
     1. 用 `probe_colocate.py` 在同样的最坏情况序列上（8192 token，completion 1024），在 colocate 模式下测一遍关掉检查点后的训练端峰值。
     2. 峰值不超过 18 GiB 才关；超过就保持开着，跳过这一项。
     3. 关的话，把 `cuda_memory_limit_gib` 调到实测峰值的约 1.2 倍，并且保证 0.45 × 39.5 GiB 加这个上限不超过 37 GiB；`gpu_memory_utilization` 不动。
     4. **等价性检查**：取过拟合第 1 步的同一批序列（或者从中固定抽 32 条），从同一份适配器状态出发，分别在检查点开和关的情况下各算一次 loss 和梯度。要求：loss 的绝对差不超过 1e-4；把全部 LoRA 参数的梯度拼成一个向量，两次的相对 L2 差不超过 1e-3。超出就保持开着，并报告实测的差。
     5. 报告训练时间省了多少。
   - **KL 随机抽样**：`kl.max_sequences` 设为 64。改成按 `(seed, step)` 固定种子从这一步的全部序列里随机抽，不能取前 64 条，前 64 条会偏向排在前面的几道题。日志里记下这一步实际参与 KL 估计的序列数。测试：同一个 `(seed, step)` 抽到的序列相同；抽到的序列不全是前 64 条。KL 只是监控项（β=0），这项改动不影响训练。
   - 不做序列打包，不改 `n_tasks`、`group_size`、学习率、温度、top_k、LoRA。
5. **训练期间的 dev 评测改成 K=8**，包括第 0 步的基线。题目仍是 dev 集 100 题，T=0.8、top_k 20。
   - 检查点的选法不变：选严格解出率最高的；相差不到 1 个百分点时，选步数更早的。
   - 在 `HELDOUT-PREREG.zh-CN.md` 的"修订记录"里补一条：日期、"选检查点用的 dev 评测由 K=4 改为 K=8"、理由（100 题 K=4 的噪声约 ±5 个百分点，K=8 能减小约三成，结果更可靠），并注明这条修订在正式 GRPO 开始前提交。
   - 留出集评测仍是 K=4，不变。
6. **20 小时的门槛取消。** 用户确认预算充足，训练质量优先。`bench.sh` 跑 3 步测速，只报告估算，不因为时间长而停。估算超过 40 小时才停下报告，这时多半是哪里出了问题。
